# LumenX 的后续增强

> 2026-10-19评审说明：第1～5节保留晨会原始建议，属于候选方案，不代表当前实现或已接受的技术选型。采纳范围、事实修正、暂不采用项及理由统一见文末“本轮评审结论”。原文中的商业收益、许可概括和性能数字不能直接作为验收承诺。

### 1\.OpenCue \+ Kubernetes KEDA — 分布式任务调度引擎

**开源协议**：OpenCue（Apache\-2\.0）、Kubernetes（Apache\-2\.0）、KEDA（MIT）

**补 LumenX 短板**：原生是单任务串行、单节点执行，没有集群调度能力；多人同时使用会排队阻塞，批量生成任务无法并行，无法支撑团队化 / 企业级商业化生产。

**原生感接入方式**： 

**后端层**：将 LumenX 所有耗时任务（视频生成、图像生成、转码、合成、抽帧）全部拆解为 OpenCue 作业，通过 FastAPI 接入调度器；任务状态、进度实时回传 LumenX 前端，在原生进度条组件上统一展示，用户无感知。

**资源层**：对接 Kubernetes \+ KEDA，根据任务队列长度自动扩缩 GPU 节点，高峰自动扩容、低谷自动缩容。

**商业价值**：并发量提升，产能提升，从「单人工具」升级为「企业级生产平台」；算力利用率从 30% 提升至 85% 以上，大幅降低单位视频生成成本。

---

### 2\.MinIO \+ 统一元数据引擎 — 全局对象存储与资产底座

**开源协议**：MinIO（AGPL\-3\.0，商业使用免费）、PostgreSQL（PostgreSQL 协议）

**补 LumenX 短板**：原生文件存储在本地服务器，没有统一资产库；素材、工程、成片分散存储，无法跨项目复用，没有权限管理，多份拷贝冗余严重。

**原生感接入方式**： 

**后端层**：将 LumenX 所有文件读写全部替换为 MinIO S3 接口，统一存储剧本、角色资产、场景素材、分镜工程、生成视频、成片导出；所有文件元数据写入 PostgreSQL 统一管理。

**UI 层**：在 LumenX 左侧导航栏新增「资产库」入口，和原生「剧本编辑器」「分镜编辑器」同级；支持文件夹分类、缩略图预览、权限管理，完全复用原生的卡片样式、hover 交互、右键菜单。

**流程打通**：分镜生成的角色、场景自动入库；项目中可直接从资产库拖拽素材到时间线，无需本地上传。

**商业价值**：资产全局复用，避免重复生成相同角色 / 场景，素材利用率提升 60%；统一权限隔离，满足企业级数据安全要求；是后续所有智能检索、版本管理、协作审片的底层数据基础。

---

### 3\.全链路视频质量增强管线（Real\-ESRGAN \+ CodeFormer \+ RIFE \+ VEnhancer 2\.0）

**开源协议**：均为 MIT / 学术开源，非商业免费商用

**补 LumenX 短板**：原生只做基础生成，没有超分、人脸修复、补帧、去闪烁等质量优化；AI 生成视频普遍存在分辨率低、人脸崩坏、卡顿、闪烁等问题，直接影响成片交付质量。

**原生感接入方式**： 

**后端层**：封装为「质量增强」标准计算节点，接入 OpenCue 统一调度；支持 4K 超分、人脸修复、60fps 补帧、去闪烁、去噪 5 项能力，可组合使用。

**UI 层**：在 LumenX 时间线编辑器顶部新增「一键增强」按钮，下拉选择增强档位（流畅 / 高清 / 电影级）；也可选中单个镜头单独增强，参数面板嵌入原生右侧属性栏，样式、间距、控件完全对齐原生设计。

**流程打通**：生成完成后可自动触发增强，也可在导出前选择增强方案；增强后的视频自动替换原镜头或存入资产库。

**商业价值**：成片质量直接提升一个档次，解决 AI 视频最影响观感的核心痛点；可推出「基础版 / 高清版 / 4K 版」分级交付，形成差异化定价；减少人工后期修复成本，单条视频后期时间缩短 70%。

### 4\.跨镜头角色与画风一致性引擎（InstantID \+ 风格一致性 LoRA 管线）

**开源协议**：InstantID（Apache\-2\.0）、LoRA 训练代码（MIT）

**补 LumenX 短板**：原生只有全局风格定调，没有逐镜头的角色一致性约束；多镜头生成时容易出现角色脸变、服饰变、画风漂移，是短漫剧量产的最大障碍。

**原生感接入方式**： 

**后端层**：在 LumenX 的「角色定制」环节新增「角色特征锚定」功能，上传 1 张角色参考图，自动提取身份特征 \+ 风格特征，生成一致性控制参数；所有该角色的镜头生成时自动注入参数，保证跨镜头统一。

**UI 层**：在原生「角色管理」面板中新增「一致性锁定」开关，开启后全项目该角色自动套用特征锚定；可调节「相似度 / 灵活度」滑块，完全嵌入原生属性栏布局。

美术风格同理：上传 1 张风格参考图，全片所有镜头自动锁定画风，避免逐镜头风格漂移。

**商业价值**：长视频 / 多集漫剧的角色一致性从 40% 提升至 90% 以上，满足量产要求；减少人工修图、重生成的返工率，生产效率提升 50%；支持 IP 角色固定化，打造系列化内容，提升 IP 商业价值。

---

### 5\.视频版本管理与差异对比（Git LFS \+ 自研视频 diff 工具）

**开源协议**：Git LFS（MIT）

**补 LumenX 短板**：原生没有版本管理，改稿覆盖原文件，无法回溯历史版本，无法对比两个版本的差异。

**原生感接入方式**： 

**后端层**：每次保存项目自动生成版本快照，大文件存在 MinIO，版本记录存在 Git；支持版本备注、标签、回滚。

**UI 层**：在项目顶部新增「版本历史」按钮，弹出版本列表；支持双屏对比（左右分屏同时播放两个版本），样式复用原生弹窗组件。

**流程打通**：审片通过后自动生成正式版本，可标记为 V1\.0、V2\.0，支持版本间导出差异报告。

**商业价值**：解决改稿混乱问题，所有版本可追溯，避免误删；方便对比不同方案的效果，快速决策；满足企业级项目的版本管控要求。

## 本轮评审结论（2026-10-19）

评审依据：当前代码、10月16日MongoDB切换与双ComfyUI实测、[三周计划](agents/deliverables/2026-10-13-后端差距评估与三周实施计划.md)、[本周计划](agents/deliverables/2026-10-19-本周后端实施安排.md)及本节列出的官方资料。本轮只更新文档，不部署新服务、不改数据库、不改前端。A/B各有独立GPU已由用户确认，不再重复核验。

### 一、合理建议的吸收方式

| 原建议 | 处理结论 | 合并后的可执行方案 | 进入哪个阶段 |
|---|---|---|---|
| 1. 长任务统一调度、状态回传、按资源分配 | 采纳目标，调整实现 | 一个LumenX仓库，MongoDB jobs，独立单活monitor；每实例原子占用，记录排队/生成/下载/清理阶段、种子与参数；API先提供状态查询 | 本周主线，先H3，图片/TTS/合成逐步迁入 |
| 2. 统一资产元数据与存储访问 | 采纳目标，保留现有基础 | 元数据继续用`lumenxdb`；抽中性媒体访问层，保留`output/`为本地事实文件，可选对象存储镜像/远端副本；补哈希、来源job、版本和关联 | 本周先满足H3归档；完整资产索引/存储适配后续 |
| 3. 超分、修复、补帧、去闪烁等质量增强 | 有条件采纳 | 作为独立、默认关闭的后处理job；一次选择一项做原片/增强片对照；保留原片，不自动替换已选版本 | 核心生成/合成稳定后专项，具体模型不预先锁定 |
| 4. 角色与风格参考的统一约束 | 采纳目标，先用已测能力 | 保存角色/风格参考资产及版本；由受控Qwen编辑/H3参考工作流复用；记录引用顺序、模型、工作流及参数，允许人工审阅 | 先补来源记录；多参考/身份评分/LoRA另行验证 |
| 5. 版本、备注、标签、回滚及差异信息 | 采纳目标，调整存储 | 复用已有文档快照，后续新增MongoDB项目版本及不可变媒体引用；优先在重解析/覆盖资产/合成发布前保存检查点；先做文本/参数/媒体引用差异 | 纳入安全补强，不挤掉本周任务层；视频画面对比后续 |
| 历史剧本调研：规则优先、结构化输入、中文格式、AI建议可选择 | 采纳原则，复用现有编辑器/解析器 | 文档revision/内容哈希与派生分镜关联，解析先预览/校验后应用，保留稳定实体ID；文本用既有LLM配置，不强制换回Qwen | 作为后续解析增强，前端只交接接口约定 |

自动采集生成文件的`media_assets`元数据，与自动推广到跨项目共享资产库是两件事。共享资产继续显式选择/推广，避免草稿、失败产物和未确认人设污染公共库；鉴权由业务层实现，不能只依赖对象存储的桶权限。

### 二、需要纠正的现状描述

- 当前不是“完全单任务串行”：代码使用线程池和FastAPI BackgroundTasks，但缺少独立持久化调度与跨进程恢复。不能把进程内并发当作工业级队列，也不能把既有并发说成不存在。
- 当前已有`GlobalAssetLibrary`、系列/项目资产分层及变体选择；缺的是统一媒体索引、授权、版本和智能检索，不必再从零造第二套资产库。
- 231业务元数据已于10月16日切换MongoDB；媒体仍在`output/`，并保留OSS可选能力。MinIO不等于必须替换数据库。
- 当前已有Tiptap `ScriptEditorShell`、Fountain/FDX/TXT导入、前端Fountain/FDX序列化导出、文档保存/快照/恢复接口。PDF/DOCX后端导出有依赖缺失降级分支，需验证真实部署输出，不能把历史调研的“完全没有编辑器/格式/版本”套用到现在。
- 文档快照只保护编辑稿，不保护项目全部角色、分镜、视频任务及媒体关联；此前资产丢失风险仍需项目级版本机制处理。

代码证据：`src/apps/comic_gen/api.py`的`document/*`与`_parse_fountain/_parse_fdx`；`frontend/src/components/modules/ScriptEditor/ScriptEditorShell.tsx`及`dialogs/serializers.ts`；`src/apps/comic_gen/models.py: GlobalAssetLibrary`；`src/persistence.py`。这是代码存在性核对，不是本轮重新做完所有功能验收。

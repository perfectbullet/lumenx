# 双 ComfyUI 实例检查与分工

检查日期：2026-10-16（北京时间）。用户已明确用途为 **单人开发和少量演示**。

**后续真实验收更新（同日）：**A/B的H3、Qwen文生图、Qwen3-TTS均已通过真实短样本；B另通过单参考图编辑。原文以下“未做生成”描述保留为首次只读检查记录，以[三模态实测与后端适配](./2026-10-16-ComfyUI三模态实测与后端适配.md)为最新结果。脚本、4份受控模板、7份提交/History与媒体样本已保留。

## 结论

**两实例可以先作为当前后端 MVP 的开发基线，暂不增加租用数量。**推荐 A 专注 H3 视频，B 排队执行图片与 TTS；此结论针对开发规模与资源分工，不是生成质量、速度或生产并发 SLA 的验收。

用户已明确确认A、B的GPU相互独立，作为部署事实采用，无需额外测试或证明。两端可并行执行任务，分别管理实例占用与模型清理；同一实例内的图片、TTS或视频任务仍按计划排队。

## 2. 模型与工作流能力

两边注册的节点名称集合一致；部分节点定义中的枚举/缓存列表存在差异，不按 JSON 字节完全相同认定环境一致。对之前选择的 10 个 API 工作流和 2 个 TTS UI 工作流检查，顶层所需节点在两端均存在。

## 3. 两实例如何使用

- **A 主跑 H3**：先维持已验收的参考图生视频路径，不在视频任务间频繁切换图像/TTS 模型。
- **B 主跑图片和 TTS**：图片任务与语音任务仍排队执行；先验证 Qwen 图像和 Qwen3-TTS 各一条最小工作流。
- **备用能力**：B 的 H3 经真实验收后，才考虑在没有图片/TTS积压时作为第二个视频节点；未验收前不自动迁移视频任务。
- **任务调度**：仍采用统一 MongoDB + 独立单活 monitor；每个独立实例一个执行占用，统一处理生成、取消、清理和归档。首期不让模型自行决定无限重试。
- **清理方式**：两端没有 task-archiver 扩展，沿用已有原生 `/queue`、`/free`、`/system_stats` 观测路径；不能把 `/free` HTTP 200 当成清理已完成。启用前实测各模态卸载后的空闲基线。

没有把 B 写入旧 archiver 注册表：当前用户提供 URL 是资源检查，现有 scheduler 仍偏 CSH3 模板；在图片/TTS handler 和能力约束实现前，不应把 B 当成已验收通用生产节点。

## 4. 产能口径与扩容时机

历史 A 节点的一个约 2MP、请求 4 秒的 H3 普通 20 步真实任务生成耗时约 806 秒。仅按这一样本算，单节点理论约 4.5 段/小时；5 段约 67 分钟，10 段约 134 分钟，尚未计排队、清理、下载、失败和人工重抽。这个样本不能外推到其他参数、Turbo 或 B 节点。

对单人开发，异步等待期间可以继续后端学习/开发，A/B 分工能让视频生成与素材准备重叠，因此先用现有两台。出现以下实测情况再考虑第三台：

1. 视频队列持续积压，等待妨碍每天演示；优先增加经过验收的视频实例。
2. B 的图片任务经常阻塞短配音，影响交互；先调优任务优先级/批次，再评估语音独立服务或第三台。
3. 进入多人使用或稳定日产要求；依据实际任务数、参数分布、重抽率和空闲窗口重新算容量。

下一步先通过统一或隔离的调度入口对 B 做中文短配音、角色/场景图和参考图编辑试验，再测 A/B 同时执行不同任务。不要为了验证并发而绕开正在使用的 monitor 直接抢占在线节点。

# LumenX 后端差距评估与三周实施计划

评估日期：2026-10-13。对象：一名后端开发者，使用 Codex 编码，同时需要学习和理解系统。

证据范围：本地 LumenX `main`，HEAD `a80c8cc`；领导需求文档；本地 ComfyOps 调用指南、task-archiver 源码与 README；相关项目官方仓库。本文是规划，不代表功能已实现或线上验收通过。本次未登录 231、未运行生成任务；本地代码与线上版本是否一致留在第 1 天确认。

## 1. 先决定这三周交付什么

**推荐：保留 LumenX Studio，以现有 task-archiver + ComfyUI + MiniMax-H3 为生成后端，补任务持久化、恢复、基础合成和交付验证。三周交付可使用、可追踪、可恢复的后端 MVP。**

两周可以交付技术演示闭环；三周才有相对合理的稳定性和学习空间。领导文档全部工业级能力，单人后端在 2～3 周内不能可信地承诺完成。Codex 可以缩短编码时间，不能省掉模型推理、联调、效果评估和环境验证。

本期推荐承诺：

- 使用短剧本和已有/上传角色素材，解析为 3～5 个分镜。
- 通过统一后端接口调用已有 H3 工作流，生成视频并回填项目。
- 有稳定任务 ID，能查状态、错误和参数；重启后继续查询已有任务，不盲目重复生成。
- 视频按分镜顺序合成；优先保留 H3 原生音频，提供基础字幕文件。
- MongoDB 保存新增任务及关联信息；项目 JSON 迁移按门槛分阶段推进。
- 第三周补基础权限边界、审计、统计接口、备份恢复和部署操作文档。

本期不承诺：LoRA 训练和混合注入、自动达到 92% 身份识别、专业自动精剪、多机位/画中画、完整 OpenCue 集群、全链路纯离线、30/60 路同时 GPU 推理、85 秒生成 SLA。若这些是本次硬性验收项，必须调整工期、人员或复用条件，不能把 MVP 当完整验收。

## 3. 后端原理：先理解一条请求如何变成视频

### 3.1 当前代码链路

1. 前端发 HTTP 请求，`src/apps/comic_gen/api.py` 负责参数校验、调用业务方法、返回结果。
2. `pipeline.py` 组织项目、角色、分镜、视频任务及文件；`models.py` 定义这些对象的数据格式。
3. `llm.py` 的 `ScriptProcessor` 调用 `llm_adapter.py`，把剧本转成角色/场景/分镜等结构化数据。
4. `assets.py`、`storyboard.py` 组织图像生成；视频任务走 `create_video_task`、`process_video_task`，再按 provider 路由调用模型。
5. 当前长任务大量依赖 FastAPI `BackgroundTasks` 和进程内字典。HTTP 返回不等于 GPU 完成；进程退出会丢失后台执行上下文。
6. `pipeline` 将项目写到 `output/projects.json`，系列写 `series.json`，共享资产写 `library_assets.json`；媒体文件保存在 `output/`。
7. 合并由 `pipeline.merge_videos` 调用 FFmpeg；不是所有导出都走 `ExportManager`。必须沿真实入口看调用链。

**现有恢复逻辑特别重要：**`_recover_orphan_tasks` 会把重启后遗留的 pending/processing 视频任务标记失败，而不是继续恢复。新增 H3 远端任务时，要为其增加查询恢复分支，否则远端仍在生成，本地却显示失败。

当前 `_save_lock` 是进程内锁；JSON 文件和启动时加载的整份内存项目，不能直接支撑多进程安全写入。单纯把 `json.dump` 换成 MongoDB `replace_one` 仍可能被陈旧快照覆盖。

### 3.2 推荐的新链路

```text
现有 Studio 页面 / Swagger / 后端验收脚本
              ↓ 原有项目 API
LumenX：剧本解析 → 分镜/素材 → 业务任务与模型适配器
              ↓ HTTP（带稳定业务任务 ID）
task-archiver API：草稿、素材、工作流入队
              ↓ MongoDB 持久化任务
单个 monitor：选择空闲且兼容的 ComfyUI 实例
              ↓ 上传素材 → /prompt → /history 或 WS
231 ComfyUI + MiniMax-H3：真正执行 GPU 推理
              ↓ 生成、清理、归档
LumenX：下载媒体到 output → 更新任务/分镜 → FFmpeg 合并
```

职责记法：LumenX 管“哪个项目哪个镜头”；task-archiver 管“在哪跑、重试、清理、归档”；ComfyUI 管“执行节点图”；H3 管“推理”；MongoDB 管“记录”，不执行模型；FFmpeg 管“合成”。

暂时不再叠加 Celery/Redis/OpenCue。上层负责业务任务，下层唯一负责 GPU 执行调度，避免同一 GPU 被两套队列同时占用。

## 5. 如何复用已有 ComfyOps

### 5.1 已核实的能力及限制

本地 `task-archiver/README.md` 与源码显示：

- API 和 monitor 分开运行；MongoDB 保存调度状态，磁盘 `archive/` 保存媒体。
- `scheduler.py` 有 `occupied_server` 唯一索引，每个 ComfyUI 服务实例同时只派发一个任务；其余在 MongoDB 排队。
- 支持取消、生成重试、下载重试、远端日志和重启恢复。默认生成执行最多 3 次，即首次 + 2 次重试；不等同“失败后再重试 3 次”。
- 下载失败与生成失败分开处理，不因下载失败再花一次 GPU 成本。
- monitor 有共享目录文件锁，**当前不是多活调度集群**。多个 monitor 不可随意部署到不同文件系统。
- `server_id` 记录请求来源，不强制选择该节点；CSH3 使用被选中服务器的模板，保留模型加载器和连接关系，覆盖用户参数。
- 生成成功、显存清理确认、归档完成是不同阶段。`archived` 才表示整个任务媒体归档完成；不能看到生成成功就直接返回不存在的本地文件。

因此：优先复用服务接口，不复制整套源码进 LumenX，也不直接修改它的 MongoDB 集合。要强制“仅内网 231”，需限制可调度节点集合或新增明确的调度约束；不能只在请求里填写 `server_id=231`。

### 5.2 接入步骤

1. 固定一份已经实测的 API 格式工作流。先完成 I2V 或现有 CSH3 R2V 中最稳定的一条，不同时扩展全部模式。UI 工作流 JSON 不能直接提交 `/prompt`。
2. `POST /api/task-drafts` 创建草稿；`POST /api/task-drafts/{draft_id}/files` 上传素材。使用返回的路径标识填入工作流，避免多个用户使用相同文件名互相覆盖。
3. LumenX 先保存业务任务和预分配公共 ID，再调用 `POST /api/tasks`。请求包括 `server_id`、`prompt`、`draft_id`、`prompt_id`；`request_meta` 写入 `project_id/frame_id/task_id/trace_id`。
4. 保存 task-archiver 公共 `prompt_id`，不要把它当成 ComfyUI `remote_prompt_id`。重试后远端 ID 会变化，公共 ID 保持稳定。
5. 查询公共任务状态。目前代码有 `GET /api/tasks`，**未见按 ID 的通用任务详情路由**。建议在 ComfyOps 小范围新增 `GET /api/tasks/{prompt_id}`，直接查询单任务；短期分页扫描只可作验证，不适合作长期轮询。
6. 从返回的 `archive_url` 下载视频至 LumenX 管理的 `output/`；先写临时文件，校验后原子改名，再更新项目。保留原声并用 ffprobe 验证轨道/时长。
7. 接入取消和日志接口；给 LumenX 新任务加启动后对账。未知提交结果先查公共 ID，不创建新 ID 盲目重投。

注意提交一致性：archiver 的磁盘写入与 MongoDB enqueue 并非一个跨资源事务。崩溃可能留下目录但没有调度任务。需要“提交中”超时对账和人工修复入口；409 表示 ID 已存在，不自动等于已成功入队。

### 5.3 状态映射建议

| 下游语义 | LumenX 原有兼容状态 | 新增详情状态建议 |
|---|---|---|
| waiting/queued | pending | queued |
| preparing/submitting/running/cleanup | processing | 保存实际 phase |
| retry_wait | processing | retrying |
| 生成完成、仍在下载 | processing | archiving |
| archived，且 LumenX 本地校验通过 | completed | completed |
| 生成终态失败/下载耗尽 | failed | generation_failed / archive_failed |
| 用户取消确认完成 | 需兼容处理 | canceled；旧界面若不支持，暂映射 failed 并注明取消 |
| 服务不可达，远端结果不确定 | 保留非终态 | unknown/reconciling，告警并继续对账 |

区分“请求取消”和“确认已停止”。不要用全局 `/interrupt` 误杀其他用户任务。LumenX 不额外包一层自动生成重试，避免与 archiver 重试相乘。

### 5.4 LumenX 预计修改点

- 新增客户端/适配器，例如 `src/models/comfy_archiver.py`：上传、提交、查询、取消、下载。
- `models.py`：补 provider/工作流/profile/阶段状态及关联字段，尽量复用已有 `provider_task_id`。
- `pipeline.py`：接入创建/处理/恢复/结果回写，防止旧 orphan 恢复误标 H3。
- `src/utils/provider_registry.py`、相关模型路由和 catalog：按真实调用链接线，**只修改 `factory.py` 不够**，视频路由还在 `process_video_task`。
- catalog 生成及校验遵循 `.codex/workflows/lumenx-model-onboarding.md`。这是“新 provider + runtime + catalog”，不是加一个模型名称。
- UI 新参数和模型选项交给前端协作者；你交付接口、示例及 catalog。后端测试可直接指定合法模型/profile，不必等待新页面。

不能把云端负向提示词、seed、音频开关机械映射到 H3。先查实际节点 `object_info` 和工作流，支持才暴露，不支持就明确拒绝。

## 6. MongoDB：建议用，但分两步迁移

### 6.1 为什么适合这里

任务参数和工作流是可变化的结构化数据，且 task-archiver 已采用 MongoDB。继续使用可减少维护两种数据库的学习成本。它解决持久化和查询问题，不能自动解决幂等、远端状态恢复或显存调度。

推荐复用已有 MongoDB 实例的运维能力，但为 LumenX 建独立逻辑数据库、独立账户；先核实实际 MongoDB 所在服务器、版本、备份、容量和权限，不假设一定运行在 231。

### 6.2 第一阶段：只把新增关键记录放进去

| 集合（建议名） | 内容 | 索引建议 |
|---|---|---|
| `generation_jobs` | 业务任务、公共下游 ID、项目/镜头、状态、参数快照、提交恢复信息、结果引用 | `_id`；`(project_id, created_at)`；`(status, updated_at)`；幂等键唯一索引 |
| `job_events` | 阶段变化、错误摘要、attempt、时间、trace_id | `(job_id, created_at)`；事件去重键 |
| `media_assets` | 文件相对路径、哈希、类型、时长、大小、来源任务 | `(project_id, created_at)`；按去重策略使用哈希索引 |
| `audit_events` | 操作者、动作、资源 ID、参数变更摘要、结果 | `(actor_id, created_at)`、`(resource_id, created_at)` |

项目继续使用现有 JSON 时，保持单个 LumenX API 进程。后台对账由该进程内受控循环执行，从 MongoDB 读取未完成任务；不要让另一个 worker 同时改项目 JSON。进程退出后循环可恢复，安全来自持久记录，不依赖内存队列。

幂等键建议按 `(用户或项目范围, 客户端请求ID)` 建唯一约束；另存请求哈希。同键同参数返回原任务，同键不同参数返回冲突；用户主动“再生成”使用新请求 ID。

### 6.3 第二阶段：项目数据迁移（有余量再做）

新增 Repository 层，分别实现 JSON 与 MongoDB 存储；先每项目一条文档以兼容 `Script`，长日志、历史执行和媒体保持独立集合。然后迁移 `projects/series/library_assets`。

重要约束：不能继续以全局 `self.scripts` 旧快照全量覆盖数据库。读取和更新应按项目，使用字段级更新或 `revision` 乐观锁；冲突要重新读取并重做业务修改，而非简单重写旧对象。MongoDB 单文档原子写和条件更新可用于此目的。[官方原子性说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)

每条 MongoDB 文档存在 16 MiB 上限；视频、图片、音频不塞进项目文档，也不在本期引入 GridFS。媒体留在受管磁盘/共享存储，数据库只保存引用。[官方限制](https://www.mongodb.com/docs/manual/reference/limits/)

迁移顺序：停写并备份 JSON 和媒体清单 → dry-run 解析/数量/引用校验 → 按稳定 ID 导入新库 → 比较项目数、角色数、分镜数与媒体存在性 → 切配置 → 冒烟 → 保留旧备份。不要双写两个主存储。切换后有新写入时，回滚需导出增量/当前快照，不能直接切回旧 JSON 丢掉新数据。

**第 8 天门槛：**如果重启恢复尚未稳定，就不做项目全量迁移，三周内保持“项目 JSON + 新任务 MongoDB”。这不是完整数据库改造，但能优先保护最昂贵的生成任务。

### 6.4 开发与部署选择

- 当前 pipeline 以同步业务方法为主，可先用 PyMongo 同步 Repository，在异步路径通过线程隔离阻塞；不要为了接数据库重写全部业务为 async。全新异步服务可选 PyMongo Async，新代码不优先选 Motor。[官方迁移指南](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/reference/migration/)
- 每进程复用客户端，设置连接/操作超时；数据库故障时拒绝新生成提交，不静默降级内存执行。
- 本期用单文档条件更新和补偿对账避免跨集合事务；若确需事务，再核实副本集条件。单节点副本集也不代表高可用。
- 凭证进入环境配置/密钥管理，数据库不暴露到教学终端；应用账号最小权限。备份数据库和媒体，做一次恢复到新目录/新库的演练。
- 90 天日志保留需算容量并确认制度；仅对可过期的日志设置保留策略，不给项目、活跃任务套 TTL。
- 安装 Python 包及 Docker 构建时显式使用清华镜像：`PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`。固定兼容版本，凭证不写入提交。

## 7. 自部署 MiniMax 与纯离线的边界

本计划中的 MiniMax 指你已经部署的 **MiniMax-H3 视频生成工作流**。若另指 MiniMax 文本大模型，需要单独的文本推理部署和 `llm_adapter` 接入；视频 H3 不替代剧本解析 LLM。

| 环节 | 本期建议 | 纯离线仍需补齐 |
|---|---|---|
| 剧本解析 | 保留现有接口；有本地兼容 LLM 则配置并验证 | 本地文本模型、结构化输出质量及长文本限制 |
| 角色/场景图片 | 允许使用预置/上传图片完成演示 | 本地图像/编辑模型和统一角色素材流程 |
| 视频 | 复用 231 ComfyUI + H3 | 实测所用模式、参数、性能和节点兼容性 |
| 配音 | 优先 H3 原音频或预置音轨 | 若需精确对白/固定音色，部署本地 TTS；必要时 ASR/强制对齐 |
| 合成 | 本地 FFmpeg | 本地字体、编码器、字幕支持 |
| 运行环境 | 固定镜像和模型缓存 | 禁止运行期下载、云 API 依赖和隐式外网回退，断网验收 |

I2V、首尾帧、R2V 是不同输入契约。指南里的首帧脚本不证明生产 R2V 已通过；CSH3 导演台工作流也不能仅凭文件名推断覆盖全部官方模式。应记录工作流哈希、节点版本、模型文件/量化版本、输入数量及限制。

int4/int8/2K 是需要各自验证的配置档位，不能只更改一个字符串。保持当前可跑模板，不在本期顺便改推理框架为 vLLM-Omni。

## 8. 当前有没有 ManjuForge？为什么有人建议 Nautilus？

**当前检查到的 LumenX 代码和依赖没有接入二者；ManjuForge / Nautilus 名称出现在领导方案中，不能据此认定已经集成。**

ManjuForge 官方将其定义为 Agent Skill，偏连载叙事记忆、角色关系、剧本/分镜/提示词产出。它不是 H3 推理服务；文档设想的 HTTP 分镜接口仍需应用方实现。可借鉴其创作约束，但安装到编码助手不等于给 LumenX 增加线上能力。[官方仓库](https://github.com/mengxiujie/ManjuForge)

Nautilus 官方提供 Film IR、Film Planner、World Bible，以及 FL2VA/Ref2VA 和连续片段组织，方向更接近 H3 视频生产。其 README 同时标注 experimental alpha；公开 H3 适配走 vLLM-Omni 视频 API，不等于可直接调用你现有 ComfyUI/task-archiver。[官方仓库](https://github.com/yeahdongcn/nautilus-studio)

我的判断：建议 Nautilus 的合理原因是“视频生产和 H3 的契合度”，不是已验证的工业成熟度。两者也不是必须二选一的同类替代品。

**本期决策：保留 LumenX 解析器和界面，先接现成 H3 后端；以后再评估只引入 Nautilus 的规划能力。** 整套嵌入会带来第二套项目状态、素材权限、任务和前端，不符合单人后端三周的边界。

后续 POC 限时 1～2 天，用相同 3 份剧本比较字段完整性、人工修改时间、人物/场景引用和 H3 提示词可用性；验证超时/失败降级、接口稳定性、许可及部署依赖。明显省时再接入 `PlannerAdapter`，输出统一映射到现有 `StoryboardFrame`。未胜出就保留原解析器，不阻塞交付。

## 11. 验收清单与性能口径

| 场景 | 必须观察到的结果 |
|---|---|
| 正常生成 | 3～5 镜头可生成、回填、合成，音视频文件真实可播放 |
| 非法输入 | 缺参考图/不支持时长/profile，提交前返回明确 4xx |
| 幂等 | 同一请求重发，业务任务和下游公共任务各只有一份 |
| 重启/断连 | LumenX 重启继续查原任务；网络超时不自动制造第二次 GPU 执行 |
| 归档失败 | 已生成视频仅重试下载，完成前不显示 completed |
| 取消 | 排队任务不执行；运行任务定向取消并最终释放资源 |
| 数据恢复 | 备份恢复后任务、项目引用和媒体一致；真实 MongoDB 验证索引与并发写，不能只靠 mock |
| 权限（多用户上线门槛） | 用户不能查询、取消、下载其他用户项目；静态媒体也经过同样边界 |
| 参数追溯 | 工作流/profile、模型文件标识、prompt/seed、节点、时间、attempt 可关联 |
| 前端兼容 | 原有模型任务与项目读取不回归；新参数所需 UI 明确移交 |

性能报告分开记：提交响应时间、排队时长、实际推理时长、归档时长、端到端时长、成功/失败/取消数、队列深度和实际活跃实例数。原生视频秒数、GPU 占用秒数和业务耗时是不同指标。

粗估吞吐：可用独立推理实例数 × 3600 ÷ 单任务平均占用秒数；实例占用需计入必要清理。8 张 GPU 不一定是 8 个实例，多卡模型更不能按卡数直接算并发。P95 和 98% 成功率需约定样本数、失败定义及测试条件；几段视频不足以支持 SLA。

领导文档的 24 小时长稳测试需要独立窗口、GPU 配额和任务预算。如果安排在 D14～D15，必须提前获知对其他业务的影响；没有实际运行就标为未验证。
